# What the tool surface costs

Measured token cost of the MCP tool list, which command groups carry the weight, the caching math, and which mode fits which client.

swallowtail exposes every command as a typed MCP tool by default, and tool schemas are context: an MCP client carries its tool list into every request. That makes the size of the list a real cost, and a project that ships 337 commands owes its users a measured number. This page is that number, how it was measured, and what it means for the model you drive this with.


> **The short version**
>
> The full typed surface measures **about 56,000 tokens**. That is sized for big-context frontier models with 200K to 1M token windows and prompt caching, and those carry it comfortably. A small local model will not, and this project does not aim to serve one. If your client is context-tight, `serve --typed=false` collapses the surface to a single ~490-token tool, and the CLI needs no schemas at all.


## The numbers

Measured 2026-10-08 by driving `serve` against a live Godot 4.7.2 editor the way a real MCP client would (`initialize`, then `tools/list`), and capturing the exact payload. Tokens are estimated at four characters per token; at 3.5 characters per token the top row reads closer to 64,000.

| Surface | Tools carried | Schema payload | Estimated tokens |
| --- | --- | --- | --- |
| The CLI (shell-driving agents) | none | none | **0** |
| `serve` default (typed tools) | 338 | ~224 KB JSON | **~56,000** |
| `serve --typed=false` | 1 (`godot_run`) | ~2.0 KB | **~490** |

The 338 is the 337 built-in commands plus the generic `godot_run` escape hatch. The measured project also registers four commands of its own, which the row leaves out. They would count, because the schemas are [built live from whatever the addon registers](https://regiellis.github.io/godot-mcp-go/docs/mcp-setup#two-tool-modes), so the number will drift as commands are added. Treat it as a dated snapshot and expect it to move.

## What carries the weight

The average tool costs about 165 tokens. The spread by command group, largest first:

| Group | Tools | Estimated tokens |
| --- | --- | --- |
| `runtime` | 23 | ~3,410 |
| `node` | 18 | ~2,630 |
| `scene3d` | 7 | ~2,510 |
| `anim_tree` | 10 | ~2,120 |
| `pcg` | 3 | ~1,850 |
| `lighting` | 10 | ~1,730 |
| `physics` | 7 | ~1,700 |
| `script` | 9 | ~1,690 |
| `editor` | 13 | ~1,680 |
| `wfc` | 7 | ~1,680 |

The remaining 41 groups each cost less than that. Two things stand out. First, cost follows **parameter depth**: `pcg` spends ~1,850 tokens on three tools while `scene` spends ~1,260 on eleven, because procedural-generation commands take rich structured parameters and scene commands mostly take a path and a name. Second, no single group dominates. The heaviest is 6% of the total, so there is no one group whose removal would meaningfully change the headline number.

## What it costs in practice

The headline number is the worst case: a client that carries every schema eagerly, on the first request of a session. Three things shrink it in real use.

**Context windows are large.** Against a 200K window the full list is more than a quarter of the budget; against the 1M windows current frontier models ship, it is under 6%. The list is paid out of a budget that, on the models this tool targets, has room for it.

**Prompt caching absorbs the recurring cost.** The tool list is part of the stable request prefix, so after the first request it is served from cache. On Claude's API, cached input bills at roughly a tenth of the base input rate (checked 2026-08-05; other providers price caching similarly). Catalog changes and editor availability can change the list mid-session. `serve` refreshes live definitions and emits a notification only when they differ, including when tools disappear during an outage or return after a restart. Sessions with long idle gaps can re-pay the cache write, which bills a fraction above the uncached rate for that one request.

**Schema-on-demand clients skip most of it.** Clients that defer tool schemas and load them as needed (Claude Code does this) pay only for the tools a session actually uses. The read-only `godot://` [resources](https://regiellis.github.io/godot-mcp-go/docs/mcp-setup#read-only-resources) also let a client pull project, scene, and engine state without spending any tool turn.

## Picking a mode

| You are driving with | Use |
| --- | --- |
| A frontier model in an MCP client | The default: typed tools, full schemas, schema-guided calls |
| A client that caps tool count, or a smaller model | `serve --typed=false` (stdio) or the `swallowtail/network/http_typed` setting (HTTP endpoint): one generic tool, ~490 tokens |
| A terminal-capable agent, no MCP at all | The CLI, self-describing via `swallowtail help all` and per-command `--help`, zero schemas |
| An HTTP-capable client with no Go binary | The [editor's own MCP endpoint](https://regiellis.github.io/godot-mcp-go/docs/mcp-setup#or-connect-straight-to-the-editor-streamable-http), same two modes |

The single-tool mode still reaches all 337 commands: `godot_run` proxies any of them, and the model grounds itself with `engine.search` / `engine.class_info` instead of reading schemas. That is the same [discover-then-drive loop](https://regiellis.github.io/godot-mcp-go/docs/discover-then-drive) the typed mode uses. What it gives up is the schema hints.

## Why the default stays whole

A middle tier is imaginable: a curated "core" toolset on by default, with the rest opt-in. That would cut the headline number to something like a quarter of the full list. It is not planned, for three reasons.

First, the surface is **introspection-first by design**. Schemas are built live from the addon's own param docs, so the tool list tracks whatever the editor registers (new commands, project-local commands, whatever a newer engine exposes) with no fixed catalog to maintain. A hand-curated core set would reintroduce exactly the kind of catalog this design exists to avoid, and it would need re-curating every time the surface grows.

Second, **the model this tool assumes can carry the list**. The discover-then-drive loop and the spatial-verification workflow ask real reasoning of the model driving them. A model small enough to be hurt by 56,000 tokens of schemas is also too small to use the tool well, and trimming the list would not change that.

Third, **the escape hatches already exist**. One flag reaches ~490 tokens; the CLI reaches zero. Between those and schema-on-demand clients, a constrained client has a working answer today, without a new configuration surface to document, test, and keep honest.

If a client limitation makes both escape hatches insufficient in practice, [open an issue](https://github.com/regiellis/godot-mcp-go/issues) naming the client and model. A real reproduction is the thing that would reopen this decision.
